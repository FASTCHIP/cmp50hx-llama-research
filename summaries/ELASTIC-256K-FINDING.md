# Elastic 256K: ОПРОВЕРГНУТО — 2026-09-22

Проверка гипотезы об эластичном поведении общего unified-KV при запросе,
превышающем ёмкость слота.

## Метод

`harness/elastic_test.py` (primary 192K → 4 secondary → рост до 250K) упал на
первом же запросе с HTTP 400. Причина измерена напрямую точным зондированием
размеров промпта против живого прода.

## Результат

| prompt tokens | ответ |
|---|---|
| 4 087 | HTTP 200 |
| 65 527 | HTTP 200 |
| 70 007 | **HTTP 400** `exceed_context_size_error` |
| 196 607 | **HTTP 400** `exceed_context_size_error` |

Тело ошибки:

```json
{"error":{"code":400,"message":"request (70007 tokens) exceeds the available context size (65536 tokens), try increasing it","type":"exceed_context_size_error","n_prompt_tokens":70007,"n_ctx":65536}}
```

## Вывод

- Действующий профиль `llama-qwen.service` (`--parallel 5 --ctx-size 327680
  --kv-unified --kv-unified-per-slot 65536`) **ограничивает одиночный запрос
  65 536 токенами**.
- **Никакой эластичности нет**: запрос больше слота не ставится в очередь и не
  вытесняет secondary-запросы — он отвергается до обработки.
- Следовательно, «256K контекст» у этого профиля — это суммарная ёмкость
  сервера (327 680 на пять слотов), а не доступный одному запросу контекст.
- Гипотеза «primary 256K + secondary offload/queue» для этой конфигурации
  нереализуема без смены `--kv-unified-per-slot`.

## Важное расхождение с матрицей

Все длинноконтекстные замеры (p192k, p250k) выполнялись на вариантах
`--parallel 1 --ctx-size 262144`, где один слот получает весь контекст. Это
**другой профиль**, чем действующий прод. Сравнение длинного контекста с продом
напрямую некорректно.
