# Стенд 50.9: три независимых процесса Qwen3.8 + единая точка входа

Дата: 2026-09-24, MSK. Статус: применено на стенде и проверено end-to-end.

## Что сделано

Требование: на каждой GPU 0/1/2 — **отдельный процесс llama** с собственной копией
Qwen3.8-27B и **своим KV**; клиенты по-прежнему подключаются по одному ключу к одной
точке входа, а запросы распределяются между инстансами.

| Компонент | Порт | Что это |
|---|---|---|
| `qwen-gpu0.service` | 18081 | процесс на GPU0, своя копия модели, свой KV |
| `qwen-gpu1.service` | 18082 | процесс на GPU1, своя копия модели, свой KV |
| `qwen-gpu2.service` | 18083 | процесс на GPU2, своя копия модели, свой KV |
| `qwen-balancer.service` | **8081** | nginx, `least_conn`, единая точка входа |

Все четыре юнита: `active` + `enabled`. Прежний `qwen38-vision3-131k.service` остановлен,
`disabled`, `reset-failed`. `llama-qwen` / `bonsai-2` остаются `disabled`.

### Аргументы каждого инстанса

```
CUDA_VISIBLE_DEVICES=<N>,3
--model Qwen3.8-27B-UD-Q4_K_XL.gguf --alias Qwen3.8-27B
--mmproj mmproj-Qwen3.8-27B-Q8_0.gguf --mmproj-device CUDA1 --mmproj-offload
--split-mode none --gpu-layers 999
--host 0.0.0.0 --port 1808<N> --parallel 1 --ctx-size 131072
--flash-attn on --cache-type-k q4_0 --cache-type-v q4_0
--cache-ram 0 --cache-disk /mnt/usbsata/models/kvcache-gpu<N>
-t 6 -tb 6 -b 2048 -ub 512 --api-key-file /etc/llama-server.api-key
```

`--mmproj-device CUDA1` — индекс **относителен списку видимости** (`<N>,3`), поэтому CUDA1 =
физическая GPU3: проектор уходит с 20-ГБ карт, три процесса делят 10-ГБ GPU3.

### Распределение запросов

`/etc/nginx/qwen-balancer.conf`: `upstream { least_conn; 18081/82/83 }`, `proxy_buffering off`
(иначе ломается SSE), `proxy_read_timeout 3600s`. Провайдер Open WebUI уже смотрит на
`http://172.17.0.1:8081/v1`, поэтому клиентский контракт (URL, ключ, `model=Qwen3.8-27B`)
не менялся.

## Грабли

- **Хост-RAM 15 ГБ — узкое место, а не VRAM.** При `--cache-ram 16384` на каждый из трёх
  процессов OOM-killer убил один инстанс ещё во время загрузки. С `--cache-ram 0` и
  **последовательным** стартом (health-gate каждого до следующего) RSS после старта
  0.4-0.7 ГБ на процесс, available ~12 ГБ.
- Порядок индексов `--mmproj-device` задаётся `CUDA_VISIBLE_DEVICES`, а не физической
  нумерацией; `CUDA_VISIBLE_DEVICES=<N>,3` + `--mmproj-device CUDA1` = проектор на GPU3.
- `set -e` в скрипте деплоя обрывает его на первом `curl` к ещё не слушающему порту —
  юнит остаётся недозапущенным. Health-поллинг писать без `set -e`.
- Ошибка WebUI `Model '' was not found`, которую видел пользователь, была следствием
  остановки провайдера на время передеплоя (список моделей тянется с `:8081`). После
  подъёма балансировщика список и запросы снова 200.
