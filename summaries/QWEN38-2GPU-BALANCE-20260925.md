# Qwen3.8-27B на двух CMP 50HX: баланс слоёв, ubatch и потолок контекста

Стенд ai100gb (192.168.50.9), кампания `20260925T064249Z`. Бинарь — официальный
upstream `a02c7f5` + патч порога MMQ/cuBLAS (`GGML_CUDA_TURING_CUBLAS_MIN_M=256`).
Всё измерено в одном окне, сравнение только с эталоном того же прогона.

## Итоговый профиль (установлен)

```
CUDA_VISIBLE_DEVICES=0,1
--parallel 2 --ctx-size 262144 --kv-unified
--kv-unified-per-slot 262144
--cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on
--split-mode layer --tensor-split 1.10,0.90
--spec-type draft-mtp --spec-draft-n-max 3
-t 6 -tb 6 -b 2048 -ub 512
--cache-ram 4096          <-- исправлено (было 16384)
```

```

  256      122.8    468.9     410.1     35.17
```

Длинный контекст (p120k), ub512 против ub384:

```
плечо        PP t/s   dec t/s
ub512-long     383.1     23.99
ubalt-long     383.2     24.01
```

Уменьшение ubatch не дало прироста PP на этой сборке: на p120k варианты равны,
на коротких и средних промптах 512 быстрее на 4-8%. Выбран 512.

## 4. Layer (pipeline) против tensor

```
режим    p120K PP   dec t/s   2 клиента t/s
layer       383.0     24.20       42.61
tensor      342.7     33.83       48.69
```

Tensor даёт decode +40% и суммарную скорость двух клиентов +14%, но теряет 10.5% PP.
При приоритете «один 256K плюс нормальный второй клиент» выбран layer: просадка PP
бьёт по обработке длинных промптов, а выигрыш decode достижим и без смены режима.

## 5. Проверка на 256K (256006 токенов, 128 выходных)

```
профиль            PP t/s   dec t/s   VRAM GPU0/GPU1
1.00/1.00 ub512          258.4     15.87   15587/18759
1.10/0.90 ub512          258.3     15.88   17107/17241
1.10/0.90 ub384          263.9     15.86   16817/16639
```

При фиксированном ubatch 512 распределение 1.10/0.90 не меняет скорость на 256K
(258.26 против 258.44 PP), но убирает перекос VRAM. С `ubatch 384` получается +2.2%
на 256K — меньше порога 3%, установленного в плане, поэтому отклонено.

## 6. Дефект хост-RAM и его устранение

Симптом: сразу после 256K-запроса, при запуске второго клиента,
система убивала сервер по OOM.

```
OOM: Killed process llama-server
anon-rss: 11875524 kB (11.9 GB)
host RAM total: 15909 MB
--cache-ram 16384 (16 GiB) + --cache-idle-slots
```

Механика: при появлении нового запроса свободный слот с 256K-контекстом
сохраняется в prompt-кэш в оперативной памяти (состояние ~8.9 GB при q8_0),
и второй клиент выводит потребление за пределы 15.9 GB.

После ограничения `--cache-ram 4096`:

```
256K запрос      257.8 PP   15.90 dec   HTTP 200
два клиента      41.6 / 42.1 / 44.7 ток/с суммарно
per-request dec  23.0-25.5 ток/с
пик RSS          3.63 GB (было 11.9 GB)
свободно RAM     ~10.3 GB, OOM 0, Xid 0
```

`--cache-ram` — это потолок кэша, а не зарезервированная память; по прежним
замерам он не влияет на скорость, поэтому снижение бесплатно.

## 8. Закрытые вопросы

```

- cache-ram 16384 несовместим с 15.9 GB хоста при работе с 256K
```
