# MTP-голова Qwen3.8 на CMP 50HX: +48% decode (23.09.2026)

## Вердикт

Модель везёт собственный MTP-слой, и он включается **одной строкой флагов, без сборки
и без второй копии модели** — контекст драфта делит веса с целевой моделью.
Измеренный эффект на прод-форме: **decode +47.9% на 32K, +47.3% на 4K**, агрегат при
пяти клиентах **+37%**, приёмка драфтов 0.61. Цена — **префилл −7…−8%**: цель обязана
считать nextn-эмбеддинг и на префилле. Для чата обмен выгодный, для «длинный промпт —
короткий ответ» его нужно считать отдельно.

Перенос MTP-головы на свободную третью карту **проверен и отклонён**: decode остаётся
хорошим (+39.6%), но префилл падает на 19–22% — на каждом шаге возникает зависимость
через PCIe Gen2 **x4**, самый узкий линк стенда.

## Почему это вообще применимо

Метаданные модели (прочитано из GGUF):

```text
general.architecture         = qwen35
general.name                 = Qwen3.8-27B
qwen35.nextn_predict_layers  = 1
```

`qwen35` — тег архитектуры, а не торговое имя: именно по нему llama.cpp выбирает
реализацию, и у неё есть ровно один обученный MTP-слой. В форке этому соответствует
режим `draft-mtp`, чей собственный комментарий перечисляет три случая:
`is_mem_shared (gemma4)`, `chain_heads (step35)` и
`neither (qwen35 / qwen35moe): a single trained MTP head` — наш случай.

Ключевое: при **отсутствии** `--model-draft` контекст драфта создаётся против целевой
модели и делит её веса (`shares_model = !has_draft // an MTP context runs on the
weights of the main model`), поэтому второй копии 17.5-ГБ модели не появляется.
В журнале это видно строкой
`creating MTP draft context against the target model ...`.

## Активация

```text
--spec-type draft-mtp --spec-draft-n-max 3
(и НЕ передавать --model-draft: с ним веса не разделяются)
```

Прод-юнит сейчас передаёт `--model-draft <DFlash2> --spec-type none`; удаление
неиспользуемого draft-файла измерено нейтральным (−0.05%/+0.06%), но для MTP его
наличие мешает — режим с общими весами требует пустого слота драфта.

MTP n-max 3   p32k  497.8   30.65   0.629
контроль2     p32k  535.9   20.72    —      (закрывающий)

Дельты MTP n-max 3 к контролю того же прогона: p32k `−7.0% / +47.9%`,

**Длина драфта 3 лучше 1** (30.65 против 28.49 на 32K), хотя приёмка у короткого
драфта выше (0.846 против 0.629): выигрыш даёт не доля, а число принятых за шаг

## Перенос MTP на GPU3: измерено, отклонено

Плечо: все четыре карты видимы, модель получает нулевую долю на третьей
(`--tensor-split 1,1,1,0`), MTP-блок переезжает через `--override-tensor 'blk\.64\.=CUDA3'`,
контекст драфта — через `--spec-draft-device CUDA3`.

```text
плечо          кейс   pp      tg      acc
MTP на GPU0-2  p32k  497.8   30.65   0.629
MTP на GPU3    p32k  431.6   29.54   0.629   dpp −19.3%  dtg +42.6%
MTP на GPU3*   p32k  433.4   32.47   0.654   dpp −19.0%  dtg +56.7%
MTP на GPU0-2  p4k   569.9   36.03   0.610
MTP на GPU3    p4k   487.2   34.72   0.610   dpp −21.5%  dtg +41.9%
```

Просадка префилла устойчива — **−19…−22%** в обоих прогонах GPU3. А вот decode между
двумя прогонами разошёлся (29.54 и 32.47 при 30.65 на GPU0-2), то есть по decode это
**попадание в разброс, а не выигрыш**: плечи с переносом хуже не становятся, но и лучше
тоже. Вывод не зависит от того, какой из двух прогонов считать точным: префилл теряет
пятую часть, decode стоит на месте — вариант не проходит.

Перенос подтверждён телеметрией: на GPU3 появилось **833 МиБ** (в плечах без переноса
там ~135 МиБ), с GPU2 ушло около 2.6 ГБ. То есть блок действительно переехал — и это
не помогло: разгрузка «горячих» карт не компенсирует зависимость через x4-линк.

## Что не сработало по дороге (и почему)

Два первых прогона плеча GPU3 упали, и обе ошибки полезны:

1. `error while handling argument "--spec-draft-device": invalid device: CUDA3` —
   runner по умолчанию выставляет `CUDA_VISIBLE_DEVICES=0,1,2`, поэтому карты для
   процесса не существует. Карту нужно сделать видимой.
2. `pre-allocated tensor (blk.64.attn_q.weight) in a buffer (CUDA3) that cannot run
   the operation (NONE)` — `--device CUDA0,CUDA1,CUDA2` убирает у CUDA3 тип буфера,
   и адресовать туда тензоры нечем. `--device` и `--override-tensor` вместе
   несовместимы; работает нулевая доля в `--tensor-split`.

Флаги стоит проверять предварительно на несуществующем файле модели
(`llama-server -m /nonexistent.gguf <флаги>`): ошибка аргументов видна мгновенно,
а полная загрузка занимает минуты на плечо.

## Метод

- Один бинарник (`llama.cpp-vbbb-mmq-thresh-sm75`, ревизия `b7d4d853` + порог MMQ),
  переменная — только набор spec-флагов. Никаких пересборок.
- Контроль измерен в том же прогоне; добавлен **закрывающий контроль** (дал +0.1%,
  то есть дрейфа нет) и плечо «без draft-файла» для изоляции эффекта его удаления.
- Приёмка драфтов берётся из самих строк замера (`draft_n`/`draft_accepted`), а не из
  журнала; `draft_n = 0` означает, что драфт резидентен и бездействует.
- Сырые строки: `raw/mtp-ab-20260923T122442Z.jsonl` и `-conc-` (стенд 192.168.50.9).

## Длина драфта: свип и его предел

```text
плечо     кейс   pp      tg      acc     dtg
n-max 1   p32k  498.3   28.49   0.846   +37.5%
n-max 3   p32k  497.8   30.65   0.629   +47.9%
n-max 5   p32k  500.5   31.53   0.502   +52.1%
n-max 7   p32k  500.1   27.84   0.412   +34.3%
n-max 3   p32k  503.7   33.02   0.629   +59.4%   (повтор)
```

Приёмка падает с длиной монотонно (0.846 → 0.629 → 0.502 → 0.412), и n-max 7 явно
проигрывает. Но **выбрать между 3 и 5 по этим данным нельзя**: повтор тройки дал 33.02
против 30.65 в первом прогоне при тех же флагах и той же приёмке, то есть разброс
между плечами MTP около 8% — больше, чем разница между 3 и 5. Контроль при этом стоял
неподвижно (20.72 во всех трёх контрольных плечах), так что гуляет именно MTP-путь,
а не стенд.

Практическое следствие: сам выигрыш (+34…+59%) многократно перекрывает этот разброс,
а выбор конкретной длины — вопрос перепроверки на реальном трафике. Брать n-max 3:
наиболее проверен, дешевле по вычислениям на шаг, по префиллу не хуже остальных.

## Что это значит для сервиса

Для 5-слотового чат-профиля (нынешняя форма сервиса) MTP — крупнейший найденный
рычаг по decode: +48% на 32K и +37% агрегата при пяти клиентах. Плата — префилл;
на профиле «длинный промпт — короткий ответ» включать только после замера на реальном
миксе. Перенос на GPU3 не применять.
