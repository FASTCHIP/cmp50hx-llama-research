# Qwen3.8 на CMP 50HX: план повышения скорости llama.cpp

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Повысить prefill и/или decode Qwen3.8-27B на трёх CMP 50HX без скрытого ухудшения коротких запросов, конкурентности, качества или доступного контекста.

**Architecture:** От измеряемого профиля к чистому A/B на одном исходном форке `b7d4d85`, затем один небольшой патч выбора CUDA-матричного пути и повторный A/B. Действующий сервер остаётся эталоном; новый артефакт собирается только на CT200, устанавливается на стенде рядом со старым и получает собственный unit/rollback. Изменения драйвера и небезопасные CUDA-ветки не входят в сборку.

**Tech Stack:** verybigbadboy/llama.cpp, CUDA 12.8 sm_75, NCCL, CMake/Ninja на CT200; на `192.168.50.9` — `llama-server`, `harness/run_variant.sh`, `bench_request.py`, JSONL и системный журнал.

## Global Constraints

- Реальная конфигурация: 3×20 ГиБ Gen2 x8, `--parallel 5`, `--ctx-size 327680`, 65536 токенов на слот, KV q8_0/q8_0, mmproj Q8_0, `--spec-type none`, `-b 2048 -ub 512`.
- Сервер стенда можно автономно остановить для изолированного теста, но результат всегда завершать возвратом проверенного юнита, `/health=200` и проверкой API с текстовым и vision-запросом. Не строить CUDA на стенде (15 ГиБ RAM); не перезаписывать известный хороший пакет.
- Все проценты — только из одного A/B с одинаковой моделью, mmproj, prompt suite, слотами, clocks и версией исходников. Разделять single-client p32k, p192k/250k (другой слотный профиль), aggregate throughput при 2/5 клиентах, p4k и короткий TTFT.
- При `NVRM Xid`, потере карт/PCIe Gen2 x8, расхождении выходов или неработающем восстановлении — остановить эксперимент и сохранить журналы. `llama-bench` здесь нельзя использовать как меж-GPU baseline: он фактически кладёт модель на GPU0.
