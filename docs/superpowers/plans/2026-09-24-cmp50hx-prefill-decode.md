# План экспериментов: ускорение prefill и decode на 192.168.50.9

> Для Hermes: выполнять этапы последовательно; независимый review кода допустим в субагентах, но GPU-эксперименты исполняет только один runner. Этот документ — план, не разрешение считать эксперименты проведёнными.

## Цель и архитектура

Найти воспроизводимые улучшения PP, одиночного decode и поведения четырёх одновременных клиентов, не выдавая компромисс по качеству, контексту или функциональности за бесплатное ускорение.

Архитектура: неизменяемый baseline → отдельные однофакторные варианты → подтверждение победителей → тест взаимодействий → длительная проверка → применение только проверенного профиля. Компиляция исключительно в CT200 на 10.1.150.22; GPU-тесты на 192.168.50.9. Применение конфигурации не входит в написание этого плана.

Стек: официальный llama.cpp, CUDA 12.8/sm_75, NCCL, systemd, Python stdlib, JSONL. Без установки пакетов и компиляции на GPU-хосте.

## 2. Метрики и правило победы

Сохранять для каждого запроса:

- PP: реально вычисленные prompt tokens / prompt eval duration. cached_tokens сохранять отдельно; cache hit не считать ускорением холодного PP.
- Decode: server predicted_per_second, фактический output tokens, длительность; reasoning tokens входят в работу модели и не должны исчезать из учёта.
- TTFT: от отправки запроса до первого генерируемого токена в SSE, отдельно от первого видимого content. Reasoning и content различать.
- Межтокенная задержка: интервалы SSE на клиенте лишь приближение, поскольку chunk может содержать несколько токенов. Не называть chunk gap точной token latency без серверных временных меток.
- Для нескольких клиентов: aggregate output tokens / общее wall time от запуска группы до последнего завершения; per-request TTFT/finish latency и decode отдельно.
- HTTP, finish_reason, факт завершения [DONE], ошибки CUDA/OOM/Xid, restart count, draft_n/draft_accepted, принятые токены на шаг, VRAM peak, CPU, доступная RAM, swap-in/out, clocks/power/temp и PCIe во время нагрузки.

Критерии, задаваемые заранее:

- Основной кандидат: медианный PP или decode минимум +5%; другая ось не хуже -3%; эффект воспроизводится в парных повторах и не объясняется частотами/кэшем.
- Для шумного MTP минимум 5 парных повторов финалистов; при разбросе сравнимом с эффектом — «неубедительно», не победа.
- Публиковать paired ratios, медиану, min/max и bootstrap CI с фиксированным seed. Для малых выборок не обещать статистическую точность.
- Смешанная нагрузка: улучшение отзывчивости не покупать значительным падением aggregate throughput; порог допустимой потери согласовать, исходный ориентир 5%.
- Короткий screening имеет 3 повтора; p95 по ним не публиковать. Для p95 mixed-load — минимум 30 измерений на сценарий.
- Ошибки, усечение, пропущенные/неполные ответы исключают вариант из продвижения, но остаются в raw-данных.
- Конфигурация, ускоряющая одну ось и ухудшающая другую, попадает на Pareto-фронт и описывается как отдельный режим.

## 3. Артефакты и исполнитель

Будущая рабочая папка на 50.9: /home/fastchip/bench/upstream-a02c7f5-speed/.

Создать при исполнении:

- RESUME.md: цель, активный этап, последний завершённый вариант, PID/unit runner, baseline, ошибки, команда продолжения.
- manifest.json: commit, git diff hash, binary/library hashes, CMake flags, toolchain, unit+drop-ins, model identity, sampling и версия набора промптов.
- fixtures/: обезличенные русские/английские тексты, код, техдокументы, PNG с известным содержимым; sha256 каждого файла.
- raw/requests.jsonl: append-only; одна строка на попытку, включая FAIL.
- raw/telemetry.jsonl, logs/<variant>/, summary.json, REPORT.md, rejected-hypotheses.md.
- runner.py или run_campaign.sh, bench_client.py, aggregate.py, tests/test_harness.py.

Runner:

1. Эксклюзивный flock; второй runner завершает работу без изменения сервисов.
2. Снимок активных sibling-сервисов, полный юнит и drop-ins, PID/argv/библиотеки; baseline взять из текущего запуска, не из старой резервной копии форка.
3. До stop проверить новый бинарь, зависимости и парсинг аргументов; убедиться, что нет текущего чужого эксперимента.
4. Остановить baseline, дождаться освобождения выбранных GPU и порта. Не использовать фиксированный sleep как доказательство.
5. Стартовать вариант на закрытом тестовом :8082; контроллер имеет ключ. Единовременно только один большой inference-процесс на этих картах.
6. Health gate; не продолжать при crash/restart loop; фиксировать момент инициализации и окончания прогрева.
7. Запросы имеют индивидуальный timeout; после отсутствия прогресса ограниченное время вариант прерывается, а не ждёт часами. Длинный prefill с растущими processed tokens не считать зависанием.
8. Каждый вариант запускается заново; warmup одинаковый. Проверку cold PP обеспечивать отсутствием reuse и контролем cached_tokens, а не одним названием сценария.
9. Graceful остановка, проверка новых Xid/AER относительно сохранённого journal cursor.
10. EXIT/TERM восстановление ровно сервисов, активных до серии; отдельная проверка health, PID, argv, текста/vision и неизменности baseline.

Длительная серия запускается durable transient systemd unit с достаточным TimeoutStopSec и --no-block. Состояние обновляется после каждой строки/фазы. Watchdog только читает состояние живого исполнителя и никогда не запускает второй. При dead executor — сначала остановить оставшиеся тестовые процессы и восстановить baseline; продолжать только с корректного checkpoint. Перезапуск faulting arm автоматически запрещён.

Тесты harness до GPU-нагрузки: cache hit не входит в cold PP; HTTP 400/timeout пишется как FAIL; reasoning не теряется; отсутствующее timing поле не становится нулевой скоростью; ожидаемые строки считаются из матрицы программно; restore тестируется на искусственной ошибке запуска. Synthetic fixture в unit-тестах явно помечается как fixture, никогда не как GPU-результат.

## 4. Набор нагрузок

### 4.1 Screening

Один активный клиент при parallel=4, без изменения конфигурации слотов:

- Короткий запрос около 128–512 токенов; проверка TTFT и штрафа на маленьком M.
- p4k: 4096 реально токенизированных prompt tokens, output 512.
- p32k: 32768 prompt tokens, output 512.
- p64k: 65536 prompt tokens — только кандидаты, пережившие screening.
- Проза, код и инфраструктурная задача. Не набивать контекст одним повторяющимся словом; не добиваться искусственно высокого MTP acceptance.

Точное число токенов получать tokenizer endpoint или tokenizer из той же сборки. Чат-шаблон добавляет токены: окончательная длина — по API usage/серверу. Название p32k сопровождается фактическим count, если отличается.

Для изоляции скорости использовать output 512 с ignore_eos, если endpoint официально поддерживает это; проверять фактический count. Для качества — отдельные естественно завершающиеся ответы, не принудительная генерация мусора после EOS.

### 4.2 Gate для финалистов

- Одиночные 128K, 192K и около 250K prompts, резервировать output внутри cap.
- Никаких четырёх одновременных 256K при общем пуле 512K.
- 2 и 4 клиента: разные 4K/32K промпты, общий бюджет заведомо ниже пула.
- Mixed: один long-prefill клиент и три клиента, уже генерирующие; отдельно поступление короткого запроса во время длинного prefill.
- Cache scenarios: cold; warm prefix одного диалога; interleaved диалоги; разные prompts. Таблицы раздельные.
- Vision: одноцветные fixture PNG и реальная обезличенная картинка/документ с проверяемым ответом; text+image, streaming, неверный ключ 401.

Перед серией вычислить expected_rows из фактического списка cases × repetitions × variants и записать в manifest; retries имеют отдельный attempt, не увеличивают скрыто n успешных повторов.

### B1. Ubatch на уже изменённом cuBLAS пути — первый приоритет

- Baseline: -b 2048 -ub 512, threshold 256.
- U1024: только -ub 1024.
- U2048: только -ub 2048; выполнять лишь после VRAM gate U1024.

- Только после победы ubatch проверить -b 4096 при фиксированном ubatch: отдельная гипотеза о группировке, не смешивать два изменения.

### B2. MTP длина — второй приоритет

- n=3 baseline; n=5 кандидат; n=1 контроль; --spec-type none контроль цены самой спекуляции.
- Остальное одинаково; минимум три класса текстов.

- No-MTP может выиграть PP, но потерять decode. Это отдельный режим для long-prompt/short-answer, а не «общий победитель».

### B3. Порог MMQ/cuBLAS

- При фиксированном ubatch: env=0 (отключённый локальный патч), 128, 256 baseline, 512.
- Сначала разобрать достижимые M на коротких запросах, последнем неполном ubatch, decode/MTP verification. Порог 128/256 при полном M=512 может вести к одному пути: одинаковые результаты ожидаемы, не считать отдельным открытием.
- Проверить границы M=T-1,T,T+1 в тесте политики, dense vs MoE и не-Turing; invalid/unset env сохраняют baseline.
- PP/decode и vision; для численно изменённого пути — PPL/качество. Не использовать одинаковые текстовые hashes как тест численной эквивалентности.

### B4. RAM-кэш и CPU

- cache-ram 16384 baseline → 4096 → 8192; 0 только диагностический cold-контроль.
- Тест повторных диалогов, RAM pressure и si/so, не только одиночный PP.
- Не запускать swapoff и не чистить page cache на живом хосте.
- Если свопинга нет, считать это оптимизацией устойчивости/кэша, не ускорением CUDA.
- Затем -tb 3/6/12 при -t 6; отдельный -t 3/6/12 при фиксированном -tb. Никаких AVX2/FMA-билдов для этого CPU.
- CPU governor/affinity тестировать только при наблюдаемой зависимости задержек от частот/планировщика, с восстановлением исходного режима.

## 8. Этап D — исследовательские патчи

Разрабатывать только после B/C, каждый патч отдельным commit и runtime gate OFF по умолчанию. До benchmark: unit tests → сборка CT200 → backend correctness → functional gate → same-artifact OFF/ON A/B.

### D1. Decode-aware prefill scheduling — приоритет для четырёх клиентов

Гипотеза: выделять меньше работы новому prefill, когда другие слоты уже декодируют, и больше — когда decode отсутствует.

- Начать не с CUDA-патча, а с trace существующего scheduler и фактического chunking; возможно, upstream уже имеет подходящий механизм.
- Кандидатный файл: /root/llama.cpp-upstream-20260924/tools/server/server-context.cpp; точные функции найти по scheduler/batch формированию в pinned tree.
- Не менять размер CUDA graph/контекста произвольно. Проверить, можно ли безопасно ограничить число prefill tokens в собираемом batch без переинициализации; если нельзя — переработать гипотезу, а не переключать n_ubatch небезопасно.
- Политика: больший budget при отсутствии decode; меньший при активных decode; минимальная гарантированная доля prefill и deadline/aging против starvation.
- Тесты: один decode не блокирует prefill бесконечно; отменённый запрос освобождает бюджет; нет потери/повторения tokens; несколько waiting slots обслуживаются; prompt cache и vision позиции корректны; MTP+continuous batching сохраняет семантику.
- Основной outcome: TTFT короткого клиента и inter-chunk gap у декодирующих, при сохранении aggregate throughput. Не обещать роста чистого solo PP.

### D2. Turing matmul dispatch, shape-aware

Гипотеза: один порог M не оптимален для разных K/N/type и последних неполных блоков.

- Файлы: ggml/src/ggml-cuda/mmq.cu и локальный mmq-turing-policy.h; окружающий вызов/форматы проверить в pinned source.
- Собрать распределение реальных shapes лёгким отключаемым счётчиком, не логировать каждую операцию синхронно.
- Измерить representational microbench на этих shapes (не весь произвольный диапазон); затем выбрать маленькую детерминированную таблицу, без online-autotune в рабочих запросах.
- Не выводить модельную скорость из isolated matmul. Обязателен end-to-end с теми же prompts.
- Сохранить архитектурные, shared-memory и MoE guards. Decode/MTP small-M не отправлять в cuBLAS без отдельного выигрыша.
- test-backend-ops -o MUL_MAT с gate OFF/ON, PPL и vision; stdout/JSON результата сохранять полностью.

### D3. Повторное использование dequantized weights — условная гипотеза

Исследовать только если измерения/исходник показывают существенную цену повторной деквантизации при prefill.

- Сначала прочитать существующие buffer/cache lifetime, выяснить, не реализован ли reuse уже.
- До реализации рассчитать VRAM budget по реальным tensor sizes. Полный fp16-кэш весов при нынешнем заполнении GPU неприемлем без доказанного бюджета.
- Возможный ограниченный per-buffer/per-layer reuse только в prefill с жёстким лимитом, корректной инвалидизацией и освобождением; без CPU swap/offload ради красивого PP.
- Если безопасный budget отсутствует или экономия не покрывает управление кэшем — закрыть без сборки большой ветки.

### D4. Graph/fusion и launch overhead — по признакам CPU-bound decode

- Проверить реальные runtime gates и горячие paths в исходнике, а не угаданные env names.
- OFF/ON отдельного поддержанного механизма; не отключать все fusion одновременно.
- Исследовать CPU waits/kernel launch overhead только если telemetry показывает простаивание GPU между шагами, а не memory-bound compute.
- NVIDIA profiler на CMP ранее недоступен: ncu ERR_NVCMPGPU, nsys без CUPTI. Не планировать анализ несуществующего GPU trace. Использовать coarse host timing и содержательно ограниченные microbench.

## 9. Аппаратная ветка

- Под нагрузкой подтвердить Gen2 x8 на трёх основных картах и отсутствие AER/Xid. Не считать idle negotiated speed пределом.
- Прочитать capability GPU/root ports и актуальный topology. P2P проверять не только topo, а корректным содержимым peer copy; native remote atomics учитывать отдельно.
- Gen3/иная ширина — только если реальные capability, разводка и предыдущая история дают основания. Не повышать speed регистрами вслепую и не обещать Gen3 для CMP.
- Если bottleneck связан с interconnect в tensor режиме, сравнить только валидную размещаемую топологию; аппаратная перестановка/BIOS — отдельное окно с доступом к консоли.
- Температура/питание: измерить throttle reasons в длинном PP; мощность в idle ничего не доказывает. Не превышать допустимые пределы питания/охлаждения.
- Разгон core и смена CUDA ранее дали около шума — закрыто до новых доказательств. Не начинать с разгона памяти.
- Расширение RAM может устранить swap/cache pressure, но не объявлять его ускорением GPU без корреляции latency с si/so.

## 10. Закрытые направления и условия переоткрытия

- FORCE_MMQ: уже выбирался, null. Открывать при смене kernel dispatch/model.
- Безусловный FORCE_CUBLAS: портит short PP; наш threshold решает этот недостаток.
- Старый ubatch null на чистом MMQ не переносится на текущий cuBLAS gate — поэтому B1 открыт.
- MTP head на GPU3 Gen2 x4: PP ухудшался. Открывать только при другой топологии/подтверждённом уменьшении transfer cost.
- FA tile 64 для Turing/head_dim256: превышение shared-memory budget, CUDA/Xid. Не снимать guard; новый kernel потребует нового расчёта памяти и correctness, не «ещё одного запуска».
- Triton-engine на sm_75 без MMA: не кандидат первого ряда.
- Ngram ранее почти null; DFlash ранее зависел от класса и уступал плотному варианту. Не начинать новую кампанию с повторного перебора draft-моделей.
- GPU profiler на CMP: недоступен; не закладывать как обязательный этап.

## 11. Подтверждение и выпуск

1. Для каждого финалиста повторить baseline/candidate в чередующемся порядке и одинаковой тепловой/кэшевой фазе.
2. Проверить объединение победителей: baseline, лучший ubatch, лучший MTP, оба вместе. Сумма одиночных процентов не является прогнозом объединения.
3. Прогнать long/context/concurrency/vision gates без уменьшения исходных гарантий.
4. Для численных патчей: один fixed corpus/seed/chunks для PPL, сравнение с оценкой погрешности и направлением изменения; несколько практических QA/code задач. Это ограниченная проверка, не доказательство полной эквивалентности модели.
5. Несколько часов mixed soak для выбранного профиля: не менее двух циклов наполнения/вытеснения prompt cache, отмены и смена диалогов, long→short→vision. Продолжительность скорректировать по фактическому времени запросов.
6. Нулевые новые CUDA/Xid/OOM, без рестартов, без растущей очереди без прогресса, без утечки RSS/VRAM между одинаковыми циклами.
7. Финальный отчёт: narrow table PP/decode/TTFT/aggregate, n, контекст, cold/warm, sampling, per-stream vs aggregate; полный raw dataset и manifest.
8. Применять только проверенный профиль; сохранить актуальный upstream baseline+drop-ins для отката. Старую форковую копию не использовать как случайный rollback текущей кампании.
9. После применения прочитать exact PID/argv/libs, health, text/image/stream/auth, проверить число серверов и все ранее активные siblings. Служба active не означает правильную сборку.

## 12. Порядок выполнения и точки остановки

Первая очередь: harness/preflight → baseline → U1024 → U2048 при наличии памяти → MTP n=5 → baseline повтор → cache/RAM.

Вторая очередь: shape threshold → CPU threads по telemetry → tensor compatibility и workload verdict → объединение подтверждённых победителей.

Третья очередь: mixed scheduler patch; shape-aware dispatch лишь после дешёвых runtime тестов; projector placement только при VRAM bottleneck.

Остановиться и закрыть ветку при аппаратной ошибке, upstream incompatibility, отсутствии памяти без изменения контракта, или эффекте в пределах шума. Не добивать заранее придуманное число часов одинаковыми отрицательными тестами.

Предварительных обещаний +20/+50% нет. Срок и количество длинных запросов рассчитываются после A1 по измеренному PP; результаты по этапам сохраняются независимо от завершения всей кампании.
